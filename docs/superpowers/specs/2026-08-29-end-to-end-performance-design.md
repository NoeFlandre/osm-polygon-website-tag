# End-to-End Performance Optimization Design

## Goal

Reduce measured CPU, allocation, and SQLite round-trip overhead without
changing public APIs, Parquet schemas, row ordering, cache semantics, resume
behavior, or output bytes except for metadata that is already generated by the
existing writers.

## Baseline evidence

The clean optimization branch passed all 1,009 tests in 311.12 seconds. The
first `just check` attempt reached the build step but could not resolve
`hatchling` because the sandbox DNS blocked PyPI; the isolated `uv build`
passed when rerun with network access.

The main measured application hotspot is hostname analysis. A synthetic
5,000-row analysis with repeated website and contact hosts took 25.1895
seconds with the current implementation. A candidate that materialized both
normalized columns once took 4.5305 seconds, a 5.56x improvement. The profile
also showed 120,000 Python hostname-UDF calls and 16.9 seconds cumulative in
the hostname extraction path for a 20,000-row synthetic analysis.

The cache writer currently performs a lookup and then an upsert for every
record. SQLite supports a single `INSERT ... ON CONFLICT ... DO UPDATE ...
RETURNING` statement for this schema, so this is a second measured round-trip
reduction candidate. Its existing retry, batching, attempt-count, timestamp,
and durability contracts can remain unchanged.

Other profiled candidates are explicitly excluded: a wide one-pass cell
aggregate was slower than the existing query shape in a 500,000-row benchmark,
and deduplication still requires a global sort whose safe streaming replacement
was not established. The intentional single-thread DuckDB setting and serial
Trafilatura parsing are also left unchanged because they protect deterministic
or thread-safety behavior.

## Design

`pipeline/analyze.py` will register the existing hostname normalizer once and
materialize a temporary `canonical_hostnames` table from
`canonical_observations`. The exact and top hostname files will read their
respective projected column from that table. The SQL output expressions,
filters, grouping, ordering, filenames, and public outputs remain the same.

`web/text_cache.py` will validate the result as before, execute one explicit
SQLite upsert with `RETURNING`, convert the returned row through the existing
row converter, and call the existing mutation counter. On insert the attempt
count is one; on conflict it increments the stored count, preserving the
current behavior without the preliminary `SELECT`.

## Testing and verification

RED tests will prove that hostname normalization is evaluated once per input
field and that `record` does not call the lookup helper. GREEN will implement
only the two measured changes. Existing output, cache, lock-retry, schema,
and end-to-end tests will remain mandatory.

Synthetic benchmarks will be rerun after implementation under `/private/tmp`
only. Full `just check`, `just pre-commit`, `just pre-push`, CRAP, and scoped
mutation verification will be run before integration. No production PBF,
Seagate data root, model cache, website network, credential, or published data
will be touched.

## Non-goals

- changing inference, fetch, parser, worker, or DuckDB default settings;
- adding a dependency or a new public abstraction;
- changing cache schema, checkpoint format, outputs, or API compatibility;
- replacing the deduplication global sort without proof of equivalence;
- modifying unrelated dirty files in the main worktree.
